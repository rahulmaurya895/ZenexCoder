SECTION 2: GIT WORKTREES
================================================================================

Goal: let the user create additional working directories linked to the
same repo (different branches checked out simultaneously), and switch
NexCode's active project to one of them — useful for running an agent
task on a feature branch while keeping main checked out elsewhere.

2.1 gitHandler.js additions
    - gitWorktreeList(projectPath)
        -> uses `git worktree list --porcelain`
        -> returns [{ path, branch, head, isMain, isLocked, prunable }]
    - gitWorktreeAdd(projectPath, { newPath, branchName, createBranch,
        fromRef })
        -> `git worktree add [-b branchName fromRef] newPath [branchName]`
        -> validate newPath is outside any existing worktree path and is
           an absolute path the user has write access to
    - gitWorktreeRemove(projectPath, worktreePath, { force })
        -> `git worktree remove [--force] worktreePath`
        -> ALWAYS classify as 'git_destructive' (Phase 2A floor) —
           requires approval even in Full access mode
    - gitWorktreePrune(projectPath) -> `git worktree prune`

2.2 worktreeStore.js
    {
      worktrees: Worktree[],
      activeWorktreePath: string,
      refresh(),
      add({ newPath, branchName, createBranch, fromRef }),
      remove(worktreePath, { force }),
      openInNexCode(worktreePath)   // see 2.4
    }

2.3 WorktreePanel.jsx (new sub-tab inside GitPanel, or accessible via the
    "Worktrees" card in Connections Hub — flip its status to 'available'
    in connectionRegistry.js and point settingsRoute here)
    - List of WorktreeCard.jsx, one per worktree (main worktree marked
      "(main)" and cannot be removed)
    - "+ Add worktree" form:
        - Path picker (use existing Phase 1 folder-picker dialog)
        - Branch: dropdown of existing branches OR "create new branch
          from <ref>" with text input
        - Submit -> gitWorktreeAdd -> refresh list
    - Each WorktreeCard shows: folder path (truncated, full path on
      hover), branch name, locked icon if isLocked, "Open" and "Remove"
      buttons
        - "Open" -> worktreeStore.openInNexCode(path) (see 2.4)
        - "Remove" -> confirm dialog (since git_destructive) -> shows
          Phase 2A ApprovalRequest card if status === 'pending_review' is
          required by current permission mode; on approval ->
          gitWorktreeRemove

2.4 "Open in NexCode" behavior
    - Reuses Phase 1's project-switching mechanism: adds the worktree path
      as a project entry in projectStore (Phase 1) if not already present,
      then switches the active project to it (same as opening any other
      folder). File Tree / Editor / Terminal / GitPanel all re-point to
      the new path.
    - Leave a TODO comment: "Phase 2B Part 9 may allow opening this in a
      separate popout window instead of switching the current window."
      Do not implement the popout itself here.

SECTION 3: BRANCH MANAGEMENT UPGRADE
================================================================================

3.1 gitHandler.js additions
    - gitBranchRename(projectPath, oldName, newName)
        -> `git branch -m oldName newName`; if oldName has upstream, warn
           user upstream is not auto-renamed (surface this in UI, do not
           auto-push a rename)
    - gitBranchDelete(projectPath, branchName, { remote: boolean, force })
        -> local: `git branch [-D|-d] branchName`
        -> remote: `git push origin --delete branchName`
        -> ALWAYS classify as 'git_destructive'
    - gitSetUpstream(projectPath, branchName, remoteRef)
        -> `git branch --set-upstream-to=remoteRef branchName`
    - gitMerge(projectPath, sourceBranch)
        -> `git merge sourceBranch --no-edit`
        -> on conflict, abort cleanly (`git merge --abort`) and return
           { conflict: true, files: [...] } rather than leaving the repo
           in a half-merged state without telling the UI
        -> classify as 'git_destructive' if current branch has
           uncommitted changes that could be affected; otherwise
           'medium' (file_write-equivalent)

3.2 BranchManager.jsx
    - Replaces/extends GitBranchSwitcher's dropdown with a full list view
      (opened via "Manage branches" link at bottom of the dropdown):
        - Each row: branch name, ahead/behind vs upstream, upstream name
          (or "no upstream" badge), action icons:
            - Checkout (if not current)
            - Rename (inline edit)
            - Set upstream (opens small dropdown of remote refs)
            - Delete (confirm dialog; remote checkbox if upstream exists)
            - Merge into current (only shown for non-current branches;
              opens MergeDialog.jsx)
    - Current branch row is pinned at top, highlighted with Primary
      left-border (#7C3AED).

3.3 MergeDialog.jsx
    - Shows: "Merge <source> into <current>?"
    - On confirm -> gitMerge
    - If result.conflict === true:
        - Show conflict file list, message: "Merge aborted due to
          conflicts in N files. Resolve manually in the editor, or try a
          different branch."
        - Do NOT attempt automatic conflict resolution.

SECTION 4: PUSH / PULL / FETCH
================================================================================

4.1 gitHandler.js additions
    - gitFetch(projectPath, { remote = 'origin' })
        -> `git fetch remote`; classify 'low'/'medium' (network_request +
           read), follows permission mode, never destructive
    - gitPull(projectPath, { remote, branch })
        -> `git pull remote branch`; classify 'medium', follows mode;
           if local changes would be overwritten, abort and return
           { needsStash: true } — do not auto-stash without telling user
    - gitPush(projectPath, { remote, branch, force })
        -> `git push remote branch [--force-with-lease if force]`
        -> ALWAYS classify as 'git_push' / 'git_destructive' (Phase 2A
           floor) — requires approval regardless of mode
        -> force push additionally requires the user to type the branch
           name to confirm (extra friction for destructive force-push)

4.2 GitSyncBar.jsx (placed in GitPanel header, next to branch name)
    - Three buttons: Fetch (refresh icon), Pull (down-arrow), Push
      (up-arrow), each showing a small badge with ahead/behind counts
      where relevant
    - Pull/Push trigger the Phase 2A ApprovalRequest flow per the rules
      above; on approval, call respective IPC and show a toast on
      success/failure (reuse Phase 2A 'notify:show' channel — but do NOT
      build the full Notification Center UI here, just emit the event;
      Part 10 builds the center that lists/manages these)
    - If gitPull returns needsStash: true, show a small inline choice:
      "Stash changes and pull" / "Cancel" — stash via `git stash` /
      `git stash pop` (classify stash as 'medium')

SECTION 6: NEW IPC CHANNELS SUMMARY (PART 2)
================================================================================

  'git:worktree-list'      renderer -> main
  'git:worktree-add'       renderer -> main  ({ newPath, branchName,

  'git:branch-rename'      renderer -> main  ({ oldName, newName })
  'git:branch-delete'      renderer -> main  ({ branchName, remote, force })
  'git:set-upstream'       renderer -> main  ({ branchName, remoteRef })
  'git:merge'              renderer -> main  ({ sourceBranch })
  'git:fetch'              renderer -> main  ({ remote })
  'git:pull'               renderer -> main  ({ remote, branch })
  'git:push'               renderer -> main  ({ remote, branch, force })
  'git:stash'              renderer -> main  ({ action: 'push'|'pop' })
