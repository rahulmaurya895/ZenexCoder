SECTION 2: TOOL SCHEMA MAPPING
================================================================================

Goal: The LLM needs to know what tools are available. MCP provides tools in 
JSON Schema format, but each LLM provider expects a slightly different wrapper.

2.1 mcpToolMapper.js (src/utils/)
  Export functions to transform an array of MCP tools (from Part 4):
  
  formatForOpenAI(mcpTools, serverId) ->
    Returns array of:
    {
      type: "function",
      function: {
        name: `${serverId}__${tool.name}`, // Namespaced to avoid collisions
        description: tool.description,
        parameters: tool.inputSchema       // MCP inputSchema is standard JSON Schema
      }
    }

  formatForAnthropic(mcpTools, serverId) ->
    Returns array of:
    {
      name: `${serverId}__${tool.name}`,
      description: tool.description,
      input_schema: tool.inputSchema
    }

  Namespacing is CRITICAL. If two MCP servers both expose a `query_db` tool, 
  the LLM must be able to specify WHICH server to use via the prefix.

SECTION 3: THE AGENT EXECUTION LOOP UPGRADE
================================================================================

Goal: When the user submits a prompt, gather all tools from all 'connected' 
MCP servers and pass them to the LLM.

3.1 AI Service Injection (openaiService.js / anthropicService.js)
  Modify the `runChat` and `runPrompt` methods:
  - Read `mcpStore.serverTools` for all currently connected servers.
  - Map them using `mcpToolMapper.js`.
  - Attach them to the API request payload under `tools`.
  - Update the System Prompt dynamically:
    "You have access to external tools via the Model Context Protocol (MCP). 
     Tool names are prefixed with their server ID. Use them when necessary."

3.2 LLM Response Handling
  When the LLM streams back a `tool_call` (OpenAI) or `tool_use` (Anthropic):
  1. Pause the text stream.
  2. Parse the tool name and arguments.
  3. If the tool name matches the `${serverId}__${toolName}` pattern, it is 
     an MCP tool.
  4. Dispatch this to `agentStore` to create a pending step in the ProgressTracker.

SECTION 4: PERMISSIONS GATING & TOOL EXECUTION (PHASE 2A TIE-IN)
================================================================================

Goal: MCP tools can be highly destructive (e.g., dropping a database). 
EVERY MCP tool call must pass through Phase 2A's permission system.

4.1 approvalRules.js (Phase 2A) — EXTEND
  Add a new rule:
  actionType: 'mcp_tool_call'
  riskLevel: 'medium' (Follows permission mode. If mode is "Default", asks 
             for approval. If "Auto-review" or "Full access", runs automatically 
             but logs to Review panel).

4.2 agentHandler.js & mcpHandler.js — EXECUTION
  When the agent loop intercepts an MCP tool call:
  1. Emit 'agent:approval-pending' with actionType 'mcp_tool_call'.
     Payload should include: Server Name, Tool Name, and the JSON arguments.
  2. The UI shows the ApprovalRequest card (from Phase 2A).
  3. If User Denies -> Return a tool_result to the LLM saying "User denied execution."
  4. If User Approves -> Call `mcpHandler.mcpCallTool(serverId, toolName, args)`.
  
  `mcpCallTool` implementation:
    - Look up the active MCP Client instance by `serverId`.
    - Await `client.callTool({ name: toolName, arguments: args })`.
    - Return the result (usually an array of text/image content objects) back 
      to the renderer.
  
  5. The renderer wraps the result in a `tool_result` message and sends it 
     back to the LLM. The LLM then resumes its analysis/generation.
