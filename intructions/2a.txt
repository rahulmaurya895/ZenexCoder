SECTION 3: PERMISSIONS SYSTEM
================================================================================

Three global modes, selectable in Settings > Permissions, and quick-switch
via a shield icon in TopBar (shows current mode + dropdown):

  1. "Default"
     - Every file write, file delete, terminal command, and git operation
       requires explicit user approval via ApprovalRequest card.
     - Read-only actions (read file, list directory, read git status) run
       automatically, no approval needed.

  2. "Auto-review"
     - AI may perform file writes and terminal commands automatically,
       BUT every change is logged into the Review Panel (Section 6) for
       the user to review/revert afterward. A toast notification appears
       for each batch: "AI made 3 changes — Review".
     - Destructive actions (delete file/folder, git push, git reset --hard,
       rm -rf, drop database, format) ALWAYS require approval regardless
       of mode.

  3. "Full access"
     - AI executes file writes, terminal commands, and git operations
       without per-action approval. Still logs everything to Review Panel.
       Destructive actions still require approval (same as Auto-review) —
       this floor cannot be disabled from the UI.
     - Show a persistent amber banner in TopBar while Full access is
       active: "Full access enabled — ZenexCoder can modify files and run
       commands without asking."

Per-action override:
  - User can right-click any pending approval and choose "Always allow
    this action type for this project" -> stored in
    permissionsStore.projectRules[projectPath][actionType] = 'allow'.

approvalRules.js — classify every agent action into:
  actionType: 'file_read' | 'file_write' | 'file_create' | 'file_delete'
            | 'terminal_run' | 'git_commit' | 'git_push' | 'git_destructive'
            | 'package_install' | 'network_request'
  riskLevel: 'low' | 'medium' | 'high'

  Rule table (used by usePermissions.js):
    file_read, network_request (read-only)        -> low, never blocks
    file_write, file_create, terminal_run,
    package_install, git_commit                    -> medium, follows mode
    file_delete, git_push, git_destructive          -> high, ALWAYS approval

SECTION 4: PERMISSION NOTIFICATIONS
================================================================================

Two layers:

  A. Inline (in chat / Progress Tracker):
     - ApprovalRequest.jsx card appears exactly where the action would
       happen, e.g. above the diff: "AI wants to write to src/auth.js"
       with buttons: [Approve] [Approve All] [Deny] [Edit First].
     - "Approve All" approves this action type for the rest of the run
       (not persisted beyond the session unless user also checks
       "Remember for this project").

  B. System-level toast (Electron Notification API):
     - Fired when: (a) an approval is requested while the app/window is
       not focused, (b) Auto-review batch completes, (c) Full access
       performs a high-risk-adjacent action.
     - Toast click -> focuses ZenexCoder window and scrolls to the relevant
       ApprovalRequest or Review entry.
     - Settings toggle: "Show system notifications for approvals"
       (default ON). Respect OS-level Do Not Disturb if Electron reports it.

IPC additions (electron/main.js):
  'agent:approval-request'  -> renderer -> main (creates pending approval,
                                main shows OS notification if unfocused)
  'agent:approval-response' -> renderer -> main (approve/deny/edit, with
                                actionId)
  'agent:approval-pending'  -> main -> renderer (push new pending approval
                                to ApprovalQueue)

  - Each step shows:
      icon: ○ pending | ⟳ running (spinning) | ✓ done (green) |

      title, short description
      expandable details: files touched, terminal output snippet,
      duration ("2.3s")
  - Top toolbar: [Pause] [Stop] [Skip Step] — wired to agentStore actions
    which call agentHandler.js over IPC to actually pause/kill the running
    process or skip to next planned step.
  - Per-step "Edit Step" (pencil icon) — opens a small editor to modify
    the step's instruction BEFORE it runs (only enabled while step status
    is 'pending').
  - Overall progress bar at top of PlanCard: "Step 3 of 5 — 42%".
  - When run finishes: summary footer — "Completed in 1m 12s. 4 files
    changed, 2 commands run." with a "Open Review" button (Section 6).

agentStore.js shape:
  {
    plan: { id, title, steps: [{id, title, description, status, files,
            output, durationMs}], currentStepIndex },
    runState: 'idle' | 'running' | 'paused' | 'completed' | 'error' |
              'stopped',
    pendingApprovals: ApprovalRequest[],
    startRun(plan), pause(), resume(), stop(), skipStep(id),
    editStep(id, newInstruction), resolveApproval(id, decision)

agentHandler.js (electron):
  - Executes steps sequentially, emitting 'agent:step-update' events.
  - Before any medium/high risk action, emits 'agent:approval-pending'
    and BLOCKS that step until 'agent:approval-response' is received.
  - Honors pause/stop/skip signals between steps (and mid-terminal-command
    via SIGINT for stop).

SECTION 7: FOLLOW-UP BEHAVIOR (QUEUE / STEER)
================================================================================

While agentStore.runState === 'running' (or while AI is streaming a
response), the ChatInput area shows FollowUpBar.jsx instead of being
disabled:

  - Placeholder: "Add a follow-up instruction..."
  - Two send-mode buttons next to the input:
      "Queue"  -> message is stored and will be sent to the AI as
                  additional context AFTER the current run/response
                  finishes. Shown in chat immediately with a small
                  "Queued — will send after current task" badge.
      "Steer"  -> message is injected into the CURRENT run immediately:
                  if streaming a response, this aborts the current
                  generation and re-sends with the new instruction
                  appended to context; if an agent run is in progress,
                  the instruction is inserted as a new step right after
                  the currently-executing step (plan is re-rendered in
                  ProgressTracker with the new step highlighted "Added").
  - Default mode is remembered per work mode (settingsStore.aiSettings
    .followUpDefault: 'queue' | 'steer', default 'queue' for "everyday",
    'steer' for "coding").
  - Keyboard: Enter = use default mode, Shift+Enter = newline (existing),
    Ctrl+Enter = use the OTHER mode (quick toggle).

SECTION 8: CONTEXT WINDOW USAGE DISPLAY
================================================================================

TokenMeter.jsx — small horizontal bar + label in TopBar, right side,
left of the model selector.

  - Shows: "12.4K / 200K tokens" with a colored fill bar:
      green   (<70% of model's context window)
      amber   (70–90%)
      red     (>90%)
  - Computed via useTokenUsage.js using existing tokenCounter.js:
      total = sum(tokens of all messages in active session within
              contextMessages window) + sum(tokens of attached
              files/images, estimated) + system prompt tokens.
  - Hover tooltip breaks it down: "System prompt: 0.3K · History: 8K ·
    Attachments: 4.1K".
  - When usage crosses 90%, show the existing Phase 1 warning behavior
    ("Old messages removed to fit context window") AND highlight the
    TokenMeter red with a pulse for 2s.
  - Model's context window size pulled from a small static map in
    tokenCounter.js (e.g. gpt-4o: 128000, claude: 200000, gemini: 1000000,
    ollama models: read from model metadata if available, else default
    8192) — keep this table easy to extend.

SECTION 11: DATABASE SCHEMA ADDITIONS
================================================================================

Add to electron/database.js (run as migrations, do not break Phase 1 data):

CREATE TABLE IF NOT EXISTS change_records (
  id TEXT PRIMARY KEY,
  session_id TEXT,
  step_id TEXT,
  file_path TEXT NOT NULL,
  before_content TEXT,
  after_content TEXT,
  status TEXT DEFAULT 'pending_review', -- pending_review|reviewed|reverted
  created_at INTEGER
);

CREATE TABLE IF NOT EXISTS approvals_log (
  id TEXT PRIMARY KEY,
  session_id TEXT,
  action_type TEXT,
  description TEXT,
  decision TEXT,        -- approved|denied|edited
  created_at INTEGER
);

CREATE TABLE IF NOT EXISTS automations (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  trigger_type TEXT NOT NULL,
  trigger_params TEXT,   -- JSON
  prompt_template TEXT,
  permission_mode TEXT,
  enabled INTEGER DEFAULT 1,
  last_run INTEGER,
  run_count INTEGER DEFAULT 0
);

CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts USING fts5(
  content, session_id UNINDEXED, message_id UNINDEXED
);
-- Populate via triggers on INSERT/UPDATE/DELETE of `messages`.
