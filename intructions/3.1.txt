SECTION 0: CONCEPTUAL INTRODUCTION FOR BEGINNERS
================================================================================

WHAT IS A SWARM ENGINE?
Think of Phase 2A like hiring one really smart but overworked Full-Stack Developer. 
If you ask them to build an app, they try to plan, code, and test all at once in 
a single straight line. Sometimes they make mistakes because they can't review 
their own work objectively.

Phase 3 introduces a "Swarm". Instead of one developer, you just hired a Startup:
1. You (The CEO) type: "Build a login system."
2. The AI Architect takes the prompt, looks at your Phase 1 File Tree, and 
   writes a blueprint.
3. The Architect passes the blueprint to the AI Coder.
4. The Coder writes the actual code.
5. Before showing it to you, the AI SecOps (Security Agent) checks the code. 
   SecOps finds a missing password hash and says "REJECTED: Add bcrypt."
6. The Coder fixes it.
7. Finally, they present the finished, secure code to you for Approval.

HARDWARE CONSTRAINT (8GB RAM TRICK):
We cannot run 4 different Local LLMs at the same time on an i3 processor. 
Therefore, the Core Engine will use "Persona Swapping". It uses the EXACT 
SAME loaded model (e.g., Qwen 2.5 7B from Phase 1), but clears the context 
and aggressively swaps the `System Prompt` depending on whose "turn" it is 
to speak. One brain, wearing four different hats sequentially.

SECTION 2: THE CORE ENGINE (SWARM STATE MACHINE)
================================================================================

Goal: A background loop that decides WHICH agent speaks next.

2.1 swarmHandler.js (electron/handlers/)
  - The State Machine uses a concept called "Handoffs". 
  - When an AI finishes its thought, it must output a specific JSON command 
    indicating who should speak next.
  
  Example LLM Output from Architect:
  {
    "analysis": "The user wants a login system. I have planned the DB schema.",
    "handoff_to": "coder",
    "instructions": "Implement auth.js using the plan above."
  }

  - `swarmHandler.js` intercepts this JSON, hides it from the user's main 
    chat view, and immediately sends "instructions" to the Coder's context window.

2.2 Internal Workflow Loop:
  1. `USER` sends prompt -> `ARCHITECT`
  2. `ARCHITECT` plans -> handoff -> `CODER`
  3. `CODER` writes code -> handoff -> `SECOPS`
  4. `SECOPS` analyzes.
     - If FAIL -> handoff -> `CODER` (with error details).
     - If PASS -> handoff -> `USER_APPROVAL`
  5. `USER_APPROVAL` triggers Phase 2A's Progress Tracker & Review Panel.

SECTION 4: INTER-AGENT COMMUNICATION (THE DEBATE ROOM)
================================================================================

4.1 The "Scratchpad" Memory
  When agents talk to each other, they don't need to pollute the user's main 
  chat history. 
  - `swarmStore.js` will maintain a `swarmInternalHistory` array.
  - This array is passed as context to the local LLM/Cloud API during the loop.
  - Only the *final* consensus or major milestones are written to the SQLite 
    `messages` table (Phase 1).

4.2 Preventing Infinite Loops
  - `swarmHandler.js` must implement a `max_iterations` counter (default: 5).
  - If Coder and SecOps bounce back and forth 5 times without passing, the 
    Orchestrator forcefully halts the loop and hands off to the User: 
    "SecOps and Coder cannot agree. Please intervene."

    [User] -> [Architect] -> [Coder] -> [SecOps]
  - Highlight the currently active node with a glowing CSS pulse animation so 
    the user knows exactly whose "turn" it is.
