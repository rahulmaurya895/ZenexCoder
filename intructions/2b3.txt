SECTION 2: ENVIRONMENT CONFIGURATIONS
================================================================================

Goal: give each project multiple named environment configurations (like
dev/staging/prod) that control which environment variables and which
runtime versions are active when the agent or user runs code.

2.1 Data model

  Environment object (persisted per project in electron-store under
  key `environments.<projectPath>`):
    {
      id: string,               // uuid
      name: string,             // "development" | "staging" | "production"
                                // | any user-defined name
      type: 'development' | 'staging' | 'production' | 'custom',
      isActive: boolean,        // exactly ONE per project is active
      vars: EnvVar[],           // see 2.2
      runtimeConfig: RuntimeConfig,  // see Section 3
      createdAt: number,
      updatedAt: number
    }

  EnvVar object:
    {
      id: string,
      key: string,
      value: string,
      masked: boolean,          // if true, value hidden in UI (shown as ••••)
      source: 'manual' | 'imported' | 'inherited',
      enabled: boolean          // disabled rows are skipped during injection
    }

  Only one environment per project may have isActive === true. Switching
  active env is atomic: deactivate current, activate new, persist, then
  emit 'env:active-changed' IPC event so all subsystems pick up new vars.

2.2 environmentStore.js
  {
    environments: { [projectPath]: Environment[] },
    activeEnvId: { [projectPath]: string | null },

    // selectors
    getEnvsForProject(projectPath) -> Environment[],
    getActiveEnv(projectPath) -> Environment | null,
    getActiveVars(projectPath) -> Record<string, string>,  // key->value map,
                                   // only enabled & !masked vars — this is
                                   // what gets injected into child processes

    // mutations
    createEnv(projectPath, { name, type, copyFromId? }),
    updateEnv(projectPath, envId, patch),
    deleteEnv(projectPath, envId),   // cannot delete the active env;
                                      // user must switch first
    activateEnv(projectPath, envId),

    // var-level mutations (operate on a specific env's vars array)
    addVar(projectPath, envId, { key, value, masked }),
    updateVar(projectPath, envId, varId, patch),
    deleteVar(projectPath, envId, varId),
    toggleVar(projectPath, envId, varId),    // enable/disable
    importVars(projectPath, envId, parsed),  // EnvVar[] from envParser.js
  }

2.3 environmentHandler.js (electron/handlers/)
  IPC-exposed functions:
    - envList(projectPath) -> Environment[]
    - envCreate(projectPath, { name, type, copyFromId? })
        -> if copyFromId provided, deep-copies vars + runtimeConfig from
           that env into the new one (useful for "create staging from dev")
    - envUpdate(projectPath, envId, patch)
    - envDelete(projectPath, envId)
        -> reject with { error: 'cannot_delete_active' } if active;
           UI must surface "Switch to another environment first."
    - envActivate(projectPath, envId)
        -> deactivate old, activate new, persist, emit 'env:active-changed'
    - envReadDotFile(filePath) -> raw string content of a .env file
    - envWriteDotFile(filePath, content) -> write serialized .env content
        -> classify as 'file_write' (medium risk) per Phase 2A rules
    - runtimeDetect() -> see Section 3
    - envGetActiveVars(projectPath) -> Record<string,string>
        (consumed by terminalHandler + agentHandler for injection)

  Storage: all environment data (including var values) stored via
  electron-store with safeStorage encryption — same mechanism as API
  keys (Phase 1 Section 10A). Never write unencrypted secret values to
  plain JSON on disk.

SECTION 3: RUNTIME / INTERPRETER SELECTOR
================================================================================

Goal: let the user specify, per environment, which version of each
language runtime the agent and terminal should use — so "run this Python
file" in dev uses venv/3.11 while staging uses system/3.10, without
requiring the user to manually activate environments in the terminal.

3.1 RuntimeConfig object (embedded in each Environment):
  {
    node: { mode: 'system' | 'nvm' | 'fnm' | 'path', version?: string,
            resolvedPath?: string },
    python: { mode: 'system' | 'venv' | 'conda' | 'pyenv' | 'path',
              version?: string, resolvedPath?: string,
              venvPath?: string },
    go:     { mode: 'system' | 'path', resolvedPath?: string },
    java:   { mode: 'system' | 'sdkman' | 'path', version?: string,
              resolvedPath?: string },
    ruby:   { mode: 'system' | 'rbenv' | 'rvm' | 'path',
              version?: string, resolvedPath?: string },
    rust:   { mode: 'system' | 'path', resolvedPath?: string },
    custom: [{ label: string, envKey: string, path: string }]
              // e.g. { label: "Bun", envKey: "BUN_BIN", path: "/home/user/.bun/bin/bun" }
  }

  'system' mode = use whatever is on PATH when the app launched.
  'path' mode = explicit absolute path provided by user.
  All other modes = auto-detect by interrogating the version manager.

3.2 runtimeDetector.js (src/utils/)
  detectRuntimes() -> Promise<DetectedRuntimes>
  Where DetectedRuntimes =
    {
      node:   { system?: string, nvm?: string[], fnm?: string[] },
      python: { system?: string, python3?: string,
                conda?: string[], pyenv?: string[], venvs?: string[] },
      go:     { system?: string },
      java:   { system?: string, sdkman?: string[] },
      ruby:   { system?: string, rbenv?: string[], rvm?: string[] },
      rust:   { system?: string }
    }

  Detection strategy (run all via spawn, never exec with string concat):
    - node system:   `node --version` -> parse "v20.11.0"
    - nvm versions:  parse `$NVM_DIR/alias/default` and list
                     `$NVM_DIR/versions/node/` directory
    - fnm versions:  `fnm list` (if fnm binary found on PATH)
    - python system: `python3 --version` -> "Python 3.11.9"
    - conda envs:    `conda env list --json` -> parse names + paths
    - pyenv:         `pyenv versions` -> parse version list
    - venvs:         scan `projectPath/.venv`, `projectPath/venv`,
                     `projectPath/env` for pyvenv.cfg
    - go system:     `go version`
    - java system:   `java -version` (stderr, parse first line)
    - sdkman:        list `$SDKMAN_DIR/candidates/java/` directories
    - ruby system:   `ruby --version`
    - rbenv:         `rbenv versions`
    - rvm:           `rvm list`

  All detection is best-effort; if a binary is not found or the manager
  is not installed, the corresponding entry is simply absent from the
  result — do not throw, do not warn the user about tools they haven't
  installed.

3.3 environmentHandler.js addition
  - runtimeDetect() -> runs runtimeDetector logic in main process
    (where PATH is the real system PATH, not the renderer sandbox)
    and returns DetectedRuntimes to renderer.

3.4 RuntimeSelector.jsx
  One section per runtime (Node, Python, Go, Java, Ruby, Rust, + Custom).
  Each section:
    - Header: runtime icon + name + current resolved version (or "Not
      configured" if system default)
    - Mode dropdown: system | <version manager if detected> | custom path
    - When mode = nvm/fnm/pyenv/etc.: sub-dropdown showing detected
      versions (populated from runtimeDetect() result). "Detect again"
      refresh button.
    - When mode = venv/conda: path input (or browse button) for the
      venv/conda env directory.
    - When mode = path: text input for absolute binary path + "Browse"
      button (opens existing Phase 1 file picker).
    - Below each section, resolved path shown in muted text:
      "Resolves to: /home/user/.nvm/versions/node/v20.11.0/bin/node"
    - If runtime detection yields nothing for a section, show a subtle
      "Not detected — install via system package manager or the runtime's
      version manager" info note, no error state.
  - "Custom runtime" row at bottom: add button -> { label, envKey, path }
    form; user can define arbitrary binaries (Bun, Deno, etc.).

4.2 EnvVarTable.jsx

  Displays the active env's vars as an editable table:
  Columns: [ Enable toggle | KEY | VALUE | Masked toggle | Source | Delete ]

  Rows:
    - KEY cell: plain text input, validated as a valid env var name
      (uppercase letters, digits, underscores, must not start with digit).
      Show inline red border if invalid.
    - VALUE cell: text input; if masked === true, show a password-style
      input (text hidden, eye icon to reveal) — the actual value IS stored
      and IS injected, it is only hidden in the UI to prevent shoulder
      surfing. Toggling masked on a row with an existing value does NOT
      clear the value.
    - Source badge: 'manual' (no badge, blank), 'imported' (small grey
      ".env" pill), 'inherited' (small purple "inherited" pill — reserved
      for a future feature where a base env can be shared; for now, no
      vars will have this source; implement the badge display only).
    - Enable toggle: checkbox; unchecked vars are shown with muted text
      and are excluded from injection.
    - Delete: trash icon, confirms inline ("Delete KEY?  [Delete] [Cancel]"
      replaces the row for 1 cycle) — no modal.

  "+ Add variable" row at bottom of table (always visible):
    - Blank KEY input + blank VALUE input + "Add" button.
    - On add: validates key, creates EnvVar with source 'manual', appends
      to table, clears inputs, focuses KEY input again for rapid entry.

  "Search variables" input above table: filters rows by KEY or VALUE
  substring, client-side only (no IPC for search).

  Keyboard shortcuts within table:
    Tab:        move to next cell (KEY -> VALUE -> masked toggle -> next row)
    Enter:      confirm edit of current row (save value)
    Escape:     cancel edit of current cell, revert to last saved value
    Ctrl+D:     duplicate selected row (insert below with "_COPY" suffix on key)

4.3 EnvImportExport.jsx (below EnvVarTable)

  Import section:
    - "Import from .env file" button -> opens file picker filtered to
      *.env, .env.*, *.env.local, etc. -> reads file via
      environmentHandler.envReadDotFile -> parses with envParser.js ->
      opens a preview modal showing parsed vars with checkboxes:
        "These variables will be imported. Uncheck any to skip."
        Existing keys show a "⚠ Overwrite" warning badge.
      Confirm -> envVars merged into current env with source 'imported'.
    - "Paste .env text" button -> opens a small textarea for raw pasting
      -> same preview-and-confirm flow.

  Export section:
    - "Export to .env file" button -> serializes enabled, non-masked vars
      (masked vars are EXCLUDED from .env export — show a notice:
      "X masked variables excluded from export") -> writes file via
      environmentHandler.envWriteDotFile -> Phase 2A permission check
      (file_write, medium) -> on success, show file path in a success
      toast (reuse 'notify:show' IPC channel; Notification Center UI is
      Part 10).
    - "Copy as .env text" button -> copies serialized content to
      clipboard without writing a file (no permission check needed for
      clipboard; do NOT expose masked values in clipboard copy either).

4.4 envParser.js (src/utils/)

  parseDotEnv(rawString) -> EnvVar[]
    - Handles: comments (# lines), blank lines, KEY=VALUE,
      KEY="quoted value", KEY='single quoted', KEY=value with # inline
      comment stripped, multiline values via backslash continuation.
    - Returns only valid KEY=VALUE pairs; skips/ignores malformed lines
      silently (do not throw — partial import is better than none).
    - Sets source: 'imported' on all returned vars.

  serializeDotEnv(vars: EnvVar[]) -> string
    - Only serializes enabled && !masked vars.
    - Quotes values that contain spaces, #, or special shell chars.
    - Adds a generated header comment:
      "# Generated by ZenexCoder — [timestamp]"
    - Groups vars with blank lines between any var whose key has a
      different prefix (e.g. DB_ vars grouped, AWS_ vars grouped) — infer
      grouping by splitting KEY on first underscore.

SECTION 5: ENV INJECTION
================================================================================

Goal: when the agent runs a terminal command or an automation step, the
active environment's enabled vars are automatically present as environment
variables — without the user having to manually `source .env` or export
anything.

5.1 terminalHandler.js (Phase 1) — EXTEND

  When spawning a new terminal process (node-pty), merge the active env's
  vars into the child process environment:
    const activeVars = await environmentHandler.envGetActiveVars(projectPath);
    const childEnv = { ...process.env, ...activeVars };
    // pass childEnv as env option to node-pty spawn

  This means vars defined in the active environment OVERRIDE process.env
  values with the same key. Document this behavior in a code comment.

  Also apply the RuntimeConfig (Section 3) to the spawn environment:
    - For the active env's runtimeConfig.node: if mode !== 'system' and
      resolvedPath is set, prepend the bin directory containing the binary
      to PATH in childEnv (e.g. if node resolves to
      /home/user/.nvm/versions/node/v20.11.0/bin/node, prepend
      /home/user/.nvm/versions/node/v20.11.0/bin to PATH).
    - Same logic for python, go, java, ruby, rust, and custom entries.
    - If mode === 'system', no PATH modification needed.
    - PATH prepend must be OS-aware: use ':' separator on macOS/Linux,
      ';' on Windows.

5.2 agentHandler.js (Phase 2A) — EXTEND

  Before executing any step that spawns a terminal command, call
  environmentHandler.envGetActiveVars(projectPath) and merge into the
  step's execution environment exactly as terminalHandler does above.
  Apply runtime PATH modification the same way.

  Also expose the active env's vars in the AI prompt context:
  When building the system prompt for an agent run, append a section:
    "## Active Environment: <envName>
    The following environment variables are set:
    <list of enabled, non-masked vars as KEY=value pairs>
    <masked vars listed as KEY=<masked> — value not shown>"
  This lets the AI reference env vars by name in generated code/commands
  without the user having to describe their env setup manually.

5.3 'env:active-changed' IPC event (main -> renderer)

  Emitted by environmentHandler.envActivate() after persisting the new
  active env. Renderer-side: useEnvironment.js subscribes and:
    - Updates environmentStore.activeEnvId for the project.
    - Re-renders EnvActiveBadge in StatusBar.
    - Notifies terminalHandler (via a follow-up IPC call) to re-read
      active vars on next terminal spawn (already-running terminals are
      NOT retroactively updated — inform user with a toast:
      "Environment changed. Restart terminal sessions to apply.").

5.4 EnvActiveBadge.jsx (StatusBar.jsx, Phase 1 — EXTEND)

  Placed left of the GitStatusBadge in StatusBar (Phase 1/Part 1).
  Shows: <Layers icon> envName  (e.g. "development" | "staging")
  Color coding:
    development  -> Text Secondary (neutral)
    staging      -> Warning amber (#F59E0B)
    production   -> Error red (#EF4444)
    custom       -> Primary violet (#7C3AED)
  Click -> opens EnvironmentsPanel.
  If no environments configured for the project -> badge hidden entirely.

SECTION 7: DATABASE SCHEMA ADDITIONS
================================================================================

No new SQLite tables required for this part. All environment data
(environment configs, vars, runtime configs) is stored via electron-store
with safeStorage encryption (existing mechanism from Phase 1 ApiKeyManager).

Schema key structure in electron-store:
  'environments'         -> { [projectPath]: Environment[] }
  'environments.active'  -> { [projectPath]: envId }

Persist on every mutation (createEnv, updateEnv, deleteEnv, activateEnv,
addVar, updateVar, deleteVar). Use a debounce of 300ms on var edits to
avoid hammering disk on each keystroke.

Add to approvals_log (Phase 2A table) — any .env file write goes through
Phase 2A approval flow (file_write / medium) and logs to approvals_log
with action_type: 'file_write', description: 'Export env to .env file'.
